# 酒店设施语义层设计

## 背景

2026-06-18 的一批酒店记录里，原始采集结果出现了同一业务信息的换壳：

- 旧形态把早餐写在顶层字段里，比如 `早餐价格`、`早餐形式`、`早餐菜品`、`儿童早餐政策`
- 新形态把早餐写进 `酒店政策JSON.hotelPolicyInfo.breakfast.content`
- 同一酒店在两种形态里，`每天07:30-10:00开放` 和 `周一至周日07:30-10:00开放` 只是表达不同，不是业务变化
- 儿童早餐政策的文字层面也会变，但结构化表格里的真实费率可能没变

如果直接拿原始 JSON / 文本做 diff，就会把“结构切换”误判成大量变动。

## 三层模型

1. 原始层
   - 保留上游 JSON、文本和路径，不改动
   - 作为证据和回溯来源

2. 语义层
   - 只抽业务概念，不枚举原始字段壳
   - 目前先覆盖早餐 / 儿童早餐：
     - `早餐.类型`
     - `早餐.价格`
     - `早餐.菜品`
     - `早餐.营业时间`
     - `早餐.儿童政策`
   - 语义层优先读结构化 `hotelPolicyJSON`，顶层字段只做兜底

3. 展示层
   - 飞书只展示语义层
   - 批次表、酒店明细表、变动项表都从语义层展开

## 归一化规则

- 菜品顺序不计入变动，`西式、中式` 和 `中式、西式` 视为相同
- `每天`、`周一至周日`、`周一到周日` 视为同一日程口径
- 儿童早餐政策优先使用结构化表格，按行、按列归一为稳定文本
- 价格只比较明确的早餐价格，不从时间文本里误抓数字

## 为什么这样做

语义层不是为了“把所有字段都预先列出来”，而是为了把有限业务概念固定住。

后续如果新增 `晚餐价格`，只需要往 `meal.dinner` 这类业务项里补一个语义槽位，不需要改整套 diff 引擎。

## 当前实现边界

- 先解决早餐 / 儿童早餐这一类高噪声字段
- 先让 6/18 这类“同日集中误报”降下来
- 其它设施类字段仍沿用现有结构化 diff
